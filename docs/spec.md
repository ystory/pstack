# Design and compatibility

## Purpose

The pstack project distributes skills and agents as separate Codex and Claude Code plugins while retaining a reproducible relationship to the same upstream sources. The Codex product remains `pstack-for-codex`; the Claude Code product is `pstack-cc`. Users install through their host's native marketplace and run setup to register agents and select worker executors and models. Development and artifact commands are documented in [Maintenance](stack.md); installation and usage are in the [README](../README.md).

## Sources and reproducibility

- [upstream.lock.json](../upstream.lock.json) pins the complete pstack snapshot and the Codex source revision used for inspection.
- [dependencies.lock.json](../dependencies.lock.json) pins the selected cursor-team-kit skills (`control-ui`, `control-cli`, and `deslop`) and their license.
- [distribution-policy.json](../distribution-policy.json) excludes Benny Slack reporting automation from the distribution. The reference snapshot remains intact; general Slack research is retained. New Benny entry points or references require review rather than silent reintroduction.
- [codex-runtime.lock.json](../codex-runtime.lock.json) pins the official Codex worker snapshot, selected file mappings, and digest. Its locked source lives under `upstream/codex-runtime/`.
- [patches/claude/series](../patches/claude/series) orders the Claude adaptations over the policy-filtered pristine source, selected cursor-team-kit files, and pinned official runtime. It does not replay the Codex adaptation series.
- [patches/series](../patches/series) orders the Codex adaptations. The patch baseline combines the policy-filtered pstack snapshot with the selected cursor-team-kit source files, so new upstream content is applied before the adaptations.

Source snapshots are reference material, not instructions for agents working on this repository. Codex adaptations live in `plugin/`; Claude Code adaptations live in `plugin-claude/`. Both retain upstream attribution and licenses. Source lock hashes cover sorted relative paths and file bytes; patch replay and artifact verification additionally compare file types and permissions. Symlinks are rejected.

The repository's `.agents/plugins/marketplace.json` exposes the committed `plugin/` tree through Codex's Git marketplace support. Consumers can install from the GitHub URL without building the maintainer CLI. The Git and generated local marketplaces share the `pstack-for-codex` identity.

The root `.claude-plugin/marketplace.json` exposes committed `plugin-claude/` as `pstack-cc`. A generated artifact for either target contains its selected tree under `plugin/`, native marketplace metadata, and `artifact.json` with source, patch, integrity, and recorded compatibility metadata. Codex keeps artifact schema 1. Claude Code uses separate schema 2 with target `claude-code` and its runtime lock. A fixed local marketplace can select a verified child artifact without rewriting older artifacts. Local artifact selection, installation into Codex's cache, setup, and runtime execution are separate operations.

## Codex adaptations

### Invocation and agents

The distribution preserves the upstream skill structure and explicit-invocation policy. `agents/openai.yaml` maps upstream `disable-model-invocation` declarations to Codex invocation metadata while retaining the original frontmatter. The technical names of `poteto-mode` and `make-bot-ui` use their directory slugs for callable tokens; their upstream display names remain in interface metadata.

The two upstream agent instruction bodies are also supplied as native TOML definitions. Setup registers them and a description-only `pstack-general-purpose` role. The latter carries requested model and reasoning choices without replacing the user's existing default role or adding another instruction body.

### Execution and model selection

The original 17 role keys and scalar/list shapes are preserved. Default ordinary roles use Sol 6.1 through Codex native agents; the hardest-work role uses Opus 5.5 through an existing authenticated Claude Code CLI. Candidate and reviewer lists and the cross-judge pool contain both models. Each panel entry produces an execution. Arena tries judges from another family than the parent's in pool order, then its default pool, and reports a skipped judge if none runs. Parent aliases cannot judge. This Arena exception does not relax another workflow's required different-family verifier.

Saved role choices override defaults. The Codex host accepts supported exact Claude model IDs beyond the bundled Opus default. Model IDs, reasoning efforts, and executors are separate fields. `auto` and `inherit-parent` mean the current parent's actual selection. Requirements for a different model or model family remain requirements; another execution of the same model does not satisfy them. Sonnet and Opus are the same family. Unknown families and parent aliases do not establish a required family difference. A required reviewer uses an eligible user-selected exact entry already resolved by its calling workflow; otherwise it retains the default counterpart. Its source is disclosed. No new counterpart role or priority scan is introduced.

Claude capability records share the existing combined catalog input and carry an executor, exact model, supported efforts, and inspectable per-model source. CLI detection records executable, version, required flags, global effort syntax, and unverified model execution. It does not enumerate account models. A compatible runtime retains the shipped Opus route under a `bundled-default` label when no explicit record replaces it. That label is not proof of account access. Other Claude models require a labeled host, configuration, or manual-confirmation source. Normalized catalogs retain these sources and remain stable when normalized again. Saved role shapes, schemas, default choices, and ownership remain unchanged. Offline read and resolve retain a valid selected ID without a live catalog.

Dispatch passes the resolved exact ID as `run-claude.mjs run --model ID`, separately from effort. The runner records that value in CLI arguments and request metadata, with stream-derived `observedModel` kept separate. A missing or mismatched observation remains visible and does not create a new failure policy. Omitted `--model` retains the legacy Opus default and reports `modelSelection: "legacy-default"`. Explicit selection reports `"explicit"`. Resumed calls pass the original request model explicitly. Session, tool permissions, environment, signals, and result handling retain their existing behavior.

Upstream cloud-first workers are adapted to local worktree execution. The parent passes the task, selected instructions, and required context paths to the chosen executor. This does not provide a read-only enforcement boundary or imply that an external Claude process inherits the parent's complete conversation. Managed worktrees use the host's attachment and archive lifecycle; recurring automation records its concrete local repository before scheduling.

Conversation inheritance and filesystem preparation are separate operations. A native history fork does not copy uncommitted changes or running processes into a new worktree. Interrogate prepares each review worktree with the scoped working-tree changes and keeps only failures the parent reruns against the real code. Follow the actual host's model, effort, role and history controls; use a fresh context with a complete brief when that host disallows overrides on a full-history fork. The [official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) describes configuration precedence, while the exposed tool schema controls the active invocation.

### Workflow changes in pstack 0.15.36

Orchestrate uses native coordination and a local project tracker/store instead of the deleted `orch` CLI, fixed TSV/JSON ledger and drain protocol. Each PR has one owner and a non-author verifier from another model family at its current head. Its Codex mapping preserves the upstream prohibition on orchestration scripts and polling loops. The existing Claude executor launcher remains an execution binding. PR/CI subscriptions are used only when the host exposes them; native child completion tools do not imply a PR event subscription.

Autopilot-stack follows Autopilot-full without merging and stacks only real dependencies. The upstream review bar blocks proven user-facing bugs, failed gates and shipped documentation made wrong by the change. Pre-existing base defects become follow-ups unless copied or newly reached. Wording-only changes do not require a new verifier, and opening a PR no longer automatically runs Interrogate. Interrogate's output excludes unrun concerns, so no verified findings is narrower than absence of risk. Sharpen produces a rewritten prompt rather than executing the underlying task.

The new explicit-only `statechart` and `ketchup-video` skills retain their upstream scope. Statechart checks a TLA+ model and derives Mermaid and rule-violation paths from the checked graph. It still requires reproducing a modeled code defect against the real implementation. Its first real check may install Java/TLC through mise, and SVG rendering uses Pele. Ketchup-video specifies an evidence-based subtitled video workflow without bundling a renderer. Updating the plugin does not execute either workflow or install those tools.

### Setup and ownership

Setup stores role preferences under `$CODEX_HOME/pstack-for-codex/`, defaulting to `~/.codex/pstack-for-codex/`. Registration manages only its owned agent files and exact native configuration blocks. It preserves unrelated settings, comments, permissions, and role choices, and stops on user edits, conflicting declarations, symlinks, damaged ownership records, or concurrent changes. It reuses an existing Claude CLI and authentication without installing tools or changing global Claude settings.

Preferences containing a Claude executor use schema 2. Native-only preferences use schema 1. Older native-only helpers reject schema 2 rather than discarding its executor. Earlier mixed helpers pinned to Opus reject nondefault Claude entries. A downgrade requires explicitly saving choices the older bundle supports with the current setup. Before restoring such a bundle, explicitly save Codex-only role choices with the current setup.

Updates and prior-version restores require installing the selected bundle and rerunning its setup. Before plugin removal, setup must unregister its owned agents while the bundle is still available; native plugin removal does not invoke an agent-cleanup hook. Model preferences are retained.

## Claude Code adaptations

### Target and role selection

The [accepted host design](claude-host-design.md) and [separate-distribution decision](adr/0001-separate-host-distributions.md) define the product. Claude uses the original 17 role keys and scalar/list shapes. Setup saves its own host preferences under `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/`. It leaves Codex preferences unchanged. Every real entry preserves executor, exact model, and reasoning effort. Parent aliases bind to the actual native Claude parent.

Setup shows the upstream defaults, marks unavailable Grok suggestions as needing a supported choice, and guides CLI installation and human login. It assigns no fixed Sol replacement and changes no orchestrator model. Native generated agent variants preserve each original worker body and exact selected Claude model. User edits and ownership conflicts remain explicit rather than being overwritten. Updates and restores require rerunning setup. Removal first unregisters owned agents while the bundle exists and retains preferences.

Earlier Claude bundles accepted moving aliases with context modifiers such as `sonnet[1m]`, despite the exact-model contract. Current setup and delegated workflows reject those saved preferences before resolving any role, and leave the file unchanged. Before rerunning setup, replace them in `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/models.json` with account-supported exact model IDs and reasoning efforts. Plain `auto` and `inherit-parent` keep their native-parent behavior.

An explicit `--claude-home` selects the preferences and definition target. CLI capability and authentication probes inherit the running host's environment, including its existing `CLAUDE_CONFIG_DIR`. Detection reports those two scopes separately. It does not relocate or copy credentials into the preferences target.

Execution before setup remains available. Unsaved roles use the upstream Claude adapter's native parent or disclosed Opus-alias mapping through static agents. Setup suggestions remain separate from those execution fallbacks. Readonly source sites use native definitions that exclude Write, Edit, and NotebookEdit. Why and Reflect retain full tool access. A Bash-capable agent is not an OS-level readonly boundary.

Registration retains owned model variants until explicit unregister, so staging another model cannot delete definitions referenced by saved preferences. Unselected variants retain their previous bodies until selected again or removed through unregister.

### Workflow and execution binding

[Claude Code execution](../plugin-claude/skills/poteto-mode/references/claude-execution.md) is the shared delegation reference. Native Claude selections use Agent with setup's exact-model definition. Codex selections use a foreground task command in native background Bash. The task remains attached until its real terminal outcome. The bundled [official runtime decision](adr/0002-bundle-codex-worker-runtime.md) defines the source dependency. No universal worker scheduler or relay agent is added.

The [delegation inventory](../plugin-claude/skills/poteto-mode/references/delegation-sites.json) accounts for role consumers and host-specific sites. Panels keep duplicate seats and cardinality. The Arena judge pool retains its ordering, parent-family comparison, default retry, and disclosed skip. Required different-model and different-family verifiers still require eligible selections. Retry, dropout, fresh-worker, worktree, and parent-review rules remain the calling workflow's rules.

Upstream cloud workers map to exclusive local worktrees with separately assigned machine resources. A history fork copies no files or processes. Interrogate transfers scoped tracked and untracked input into each worktree and the parent reruns findings. A native poteto-agent receives the actual skill path and reads its full body before work. Actual transcript evidence is required when chain-following is assessed.

[Claude history](../plugin-claude/skills/recall/references/claude-history.md) scopes transcripts to a repository and its registered worktrees. [Native wakeups](../plugin-claude/skills/poteto-mode/references/claude-wakeups.md) map session schedules, persistent schedulers, and configured webhook channels to their actual capabilities. Native child completion is not a PR subscription. Orchestrate preserves its prohibition on orchestration scripts and polling loops. A missing remote VM, scheduler, or inbound channel is reported at that specific step rather than silently disabling a workflow with an available local mapping.

Claude Code's [subagent reference](https://code.claude.com/docs/en/sub-agents), [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference), [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks), and [channels reference](https://code.claude.com/docs/en/channels-reference) support the host mapping. Source documentation establishes supported controls, not execution on this bundle or account. The runtime's tool schema and observed results determine the actual behavior.

## Verified scope

Verification has several layers: source inspection, automated fixtures, live execution, and release approval. Passing one layer does not establish the others. `codex.testedVersions` records binaries used for particular checks rather than promising every workflow on those versions.

Automated checks cover source integrity, patch replay, artifact bytes and permissions, independent packaged CLI execution, isolated setup lifecycle and ownership, model preference schemas, and executor contracts. Package checks use temporary consumer directories and isolated Codex or Claude homes. They do not establish live model access or complete native installation behavior.
