# Design and compatibility

## Purpose

The pstack project distributes skills and agents as separate Codex and Claude Code plugins while retaining a reproducible relationship to the same upstream sources. The Codex product is `pstack-codex`; the Claude Code product is `pstack-cc`. Users install through their host's native marketplace and run setup to register agents and select worker executors and models. Development and artifact commands are documented in [Maintenance](stack.md); installation and usage are in the [README](../README.md).

## Sources and reproducibility

- [upstream.lock.json](../upstream.lock.json) pins the complete pstack snapshot and the Codex source revision used for inspection.
- [dependencies.lock.json](../dependencies.lock.json) pins the selected cursor-team-kit skills (`control-ui`, `control-cli`, and `deslop`) and their license.
- [distribution-policy.json](../distribution-policy.json) excludes Benny Slack reporting automation from the distribution. The reference snapshot remains intact; general Slack research is retained. New Benny entry points or references require review rather than silent reintroduction.
- [codex-runtime.lock.json](../codex-runtime.lock.json) pins the official Codex worker snapshot, selected file mappings, and digest. Its locked source lives under `upstream/codex-runtime/`.
- [patches/claude/series](../patches/claude/series) orders the Claude adaptations over the policy-filtered pristine source, selected cursor-team-kit files, and pinned official runtime. It does not replay the Codex adaptation series.
- [patches/series](../patches/series) orders the Codex adaptations. The patch baseline combines the policy-filtered pstack snapshot with the selected cursor-team-kit source files, so new upstream content is applied before the adaptations.

Approved common adaptations are stored once in `patches/shared/`. Both ordered target series use `shared/NNNN-name.patch` references. How and No comments use common bodies. Upstream 0.15.42 deleted How's explainer template, so no shared body carries it. Native invocation and executor controls remain in each target's `skills/poteto-mode/references/execution.md`. Each series is compacted into themed patches in which every changed path belongs to one patch. `shared/0001-workflow-bodies.patch` changes the How and No comments bodies directly against the pristine source. `shared/0002-worker-execution.patch` adds the shared worker context and the agy references and scripts. The compaction replaced the earlier transfer patches, which deleted each host body in a target patch and added the common body in a shared patch. A patch recorded after a compaction can change a path that a themed patch owns until the next compaction. The two complete output trees remain self-contained Git installation inputs. See [the shared-authoring decision](adr/0003-shared-workflow-adaptations.md), which describes the transfer as first recorded, and [Compact the patch series](stack.md#compact-the-patch-series).

Source snapshots are reference material, not instructions for agents working on this repository. Codex adaptations live in `plugin/`; Claude Code adaptations live in `plugin-claude/`. Both retain upstream attribution and licenses. Source lock hashes cover sorted relative paths and file bytes; patch replay and artifact verification additionally compare file types and permissions. Symlinks are rejected.

The repository's `.agents/plugins/marketplace.json` exposes the committed `plugin/` tree through Codex's Git marketplace support. Consumers can install from the GitHub URL without building the maintainer CLI. The Git and generated local marketplaces share the `pstack-codex` identity.

The root `.claude-plugin/marketplace.json` exposes committed `plugin-claude/` as `pstack-cc`. A generated artifact for either target contains its selected tree under `plugin/`, native marketplace metadata, and `artifact.json` with source, patch, integrity, and recorded compatibility metadata. Codex keeps artifact schema 1. Claude Code uses separate schema 2 with target `claude-code` and its runtime lock. A fixed local marketplace can select a verified child artifact without rewriting older artifacts. Local artifact selection, installation into Codex's cache, setup, and runtime execution are separate operations.

## Codex adaptations

### Invocation and agents

The distribution preserves the upstream skill structure and explicit-invocation policy. `agents/openai.yaml` maps upstream `disable-model-invocation` declarations to Codex invocation metadata while retaining the original frontmatter. The technical names of `poteto-mode` and `make-bot-ui` use their directory slugs for callable tokens; their upstream display names remain in interface metadata.

The two upstream agent instruction bodies are also supplied as native TOML definitions. The poteto-agent body keeps upstream's fallback for a missing skill path, but it searches the installed `pstack-codex` plugin instead of Cursor's plugin directory. Setup registers them and a description-only `pstack-general-purpose` role. The latter carries requested model and reasoning choices without replacing the user's existing default role or adding another instruction body.

### Execution and model selection

Both hosts use upstream 0.15.43's nine role keys and keep each host's persistence shapes. Codex stores arrays for every role. Claude keeps scalar entries or aliases and ordered lists. Both saved configurations start with empty `roles`. A separate setup proposal exposes all roles with unresolved slots, one for a scalar, three for a panel, and two for the cross-judge pool. A sparse accepted save is valid. Missing roles resolve transparently to the actual native parent, with source `unconfigured` and original cardinality. A scalar resolves to one native-parent seat, a panel to three, and the pool to two, which follows the shapes of upstream's default lists. This replaces the prior fixed-model and unsaved native Opus fallbacks. Before setup, an unconfigured general-purpose seat without the registered pstack role uses the host-supported native general-purpose or default path with the selected model, effort, and complete task brief. Explicit task-native counterparts or arms keep their exact model and effort. Only parent-alias selections bind to the actual parent. If the host cannot preserve the selected settings, the seat reports a specific capability gap. Saved selections retain registered routing. The `poteto-agent` and `comment-sicko` custom roles require setup registration, so workflows that need them cannot run before setup.

Upstream 0.15.42 retired four role keys: `how explorer`, `how explainer`, `why investigators`, and `why synthesizer`. Upstream 0.15.43 retired four more: `hardest tasks`, `architect runners`, `reflect tooling`, and `reflect judgment, divergent, synthesizer`. On both hosts, a saved preference file that still holds any of them keeps working. `read`, `resolve`, and `budget` succeed and list the retired keys in `droppedRoles`. The helpers skip retired values, so an entry for a model that is no longer available does not block a save. The next real `write` omits the retired keys, keeps every other saved entry, and reports the dropped keys in its own `droppedRoles`. A dry run reports them and leaves the file unchanged. `resolve --role` with a retired key fails as an unknown role. Any other unknown key still fails `read`, `resolve`, and `write` and leaves the file unchanged.

Each role has its own target reasoning effort. The base is the effort of upstream 0.15.43's default for that role. `swarm workers` and the three list roles (`arena runners`, `arena cross-judge pool`, and `interrogate reviewers`) start at `high`. The other roles start at `xhigh`. Starting with upstream 0.15.45, a Gemini 4 Neon entry in a panel or cross-judge pool has its own `xhigh` base for budget previews. Upstream also migrates older Gemini panel defaults to Neon. Both ports preserve the user's exact model selection. A fixed Neon variant that cannot meet the preview target requires an explicit choice. The ladder is `low`, `medium`, `high`, and `xhigh`, and no role runs above `xhigh`. `large` keeps the base, `medium` lowers it one step, and `small` lowers it two steps. A target that would pass the bottom of the ladder stays there. A saved `unlimited` budget reads as `large`. `read`, `resolve`, `budget`, and `write` report that replacement in `replacedBudget` as `{ "from": "unlimited", "to": "large" }`, and report `null` otherwise. The next real `write` saves `large` unless its input names another budget. `write` rejects an exact entry above `xhigh` on every executor, while `read` and `resolve` still load such a saved entry unchanged. The budget label names where an `xhigh` role lands, and `resolve` reports each role's target. A budget preview keeps each exact model ID and executor and selects the highest supported effort at or below the role's target. An entry with no such effort appears in `needsChoice`. Parent aliases do not change. No bundled default model is added.

Saved exact entries take precedence. Model IDs, efforts, and executors are separate fields. Task-specific effort adjustments apply to exact selections. Parent aliases preserve the actual parent model and effort and bind to the actual native host parent and do not establish a different-family relationship. Unknown families do not establish diversity. Families follow Arena's Phase A. Fable (`claude-fable-*`) is its own family, and Sonnet and Opus belong to the same Claude family. Arena's cross-judge, Show me your work's trail reviewer, and a second opinion compare vendors instead of families, and Fable and the other Claude models are one vendor. Required verifiers use eligible exact entries already resolved by the calling workflow, in existing order, or an explicit task counterpart. They do not scan unrelated roles, add a verifier role, or rank alternatives. An unmet requirement keeps that step's existing gap outcome.

Arena preserves seat counts, dropout padding, ordered eligible judges and the unknown-parent rule. It now uses only the selected pool. Hidden family-default recovery and a default-pool retry were removed because they could dispatch an unchosen vendor or model. If no eligible selected judge runs, Arena discloses and skips the judge. This approved adaptation does not waive another workflow's required verifier.

Claude capability records retain executor, exact model, supported efforts, and per-model `host`, `configuration`, or `manual-confirmation` evidence. Runtime detection proves CLI version and syntax, with safe authentication status separate. It supplies no model capability or bundled default. Normalized catalogs retain provenance across repeated normalization. Offline read and resolve retain saved IDs without a live catalog.

`run-claude.mjs run` requires `--model EXACT_ID`, forwarded separately from effort and recorded in request metadata. Instruction and skill files are optional transport inputs; callers still provide the context their task requires. Omitted effort uses the existing Claude CLI default and records a null request effort, without a bundled fallback. A missing `--model` fails before worker launch. `observedModel` comes from the stream and may differ or be absent. Requested effort is not observed effective effort. Explicit resumed requests keep the original exact model. Existing sessions, permissions, process signals, and result handling remain. The receipt records `status` and the `stop` object that [stopped worker continuation](#stopped-worker-continuation) describes. The runner starts Claude Code with `--permission-mode auto` and adds no rule for supplied context files. Before this change, the caller gathered `Read`, `Edit`, and `Bash` rules for each task, and a missing rule refused the call. `--allowed-tool` now carries only an action the user approved after an auto-mode denial. A headless `claude-haiku-5-5` run in auto mode on Claude Code 2.1.325 read a file outside its working directory, recovered from a read of a missing file, ran `ls "app/(site)/(member)"`, and wrote a file, with no permission denials.

Upstream cloud-first workers are adapted to local worktree execution. The parent passes the task, selected instructions, and required context paths to the chosen executor. Both outbound wrappers automatically add the receiving executor's identity and one shared worker-context body to the task input.

The wrappers read supplied role, instruction, and skill paths and deliver their complete instruction bodies in deterministic code. The parent supplies paths instead of copying those bodies into its brief. Workers apply complete bodies already in context without reopening their files, including nested requests to read the same file. Paths, summaries, excerpts, and truncated bodies do not satisfy that exception. Required linked references and applied principle leaves still need their complete bodies or actual reads. Delivery establishes available instructions, not behavioral compliance.

Launching-host role preferences remain authoritative; native tool names and parent launch recipes are interpreted in the receiving harness. The original asynchronous delegation requirement remains. Native Claude `Agent` or `Task` calls use `run_in_background: true` when exposed; native Codex uses its asynchronous handles without an invented field. This adds no CLI flag, plugin registration, or permission change. This does not provide a read-only enforcement boundary or imply that an external Claude process inherits the parent's complete conversation. Recurring automation records its concrete local repository before scheduling.

Codex-managed worktrees use the host's attachment and archive lifecycle. The coordinator owns preparation and cleanup coordination. Creation that retargets its caller runs in a native child preparation context, preserving an external worker's selected executor and model. Workers use the terminal creation's absolute cwd. Host thread and attachment checks verify that the coordinator's primary checkout stays unchanged. After worker release and artifact preservation outside the temporary checkout, its attachment owner archives it. Cleanup requires an archived attachment and removal of both the checkout and Git worktree entry. Protected checkouts remain held. Ordinary Git worktrees retain Git cleanup.

An upstream cloud worker installs dependencies in its own VM. A new local worktree has none of the source checkout's ignored dependency or build directories. The [worktree setup reference](../plugin/skills/poteto-mode/references/worktree-setup.md), common to both targets, directs the repository's own worktree setup, or its documented install or build command inside that worktree. It forbids linking or sharing such a directory from another checkout, because an install, scan, or cleanup in the worktree would then act on that checkout's files. Each execution reference points to it. This adds no script or runtime check.

Conversation inheritance and filesystem preparation are separate operations. A seat that its caller launches without a role, such as How's subagent or a Recall investigator, uses the actual native parent with `fork_turns: "none"` and a complete brief. Upstream subagents start with a clean context, and a full-history fork would not. A native history fork does not copy uncommitted changes or running processes into a new worktree. Interrogate prepares each review worktree with the scoped working-tree changes and keeps only failures the parent reruns against the real code. Follow the actual host's model, effort, role and history controls; use a fresh context with a complete brief when that host disallows overrides on a full-history fork. The [official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) describes configuration precedence, while the exposed tool schema controls the active invocation.

### Setup and ownership

Setup stores role preferences under `$CODEX_HOME/pstack-codex/`, defaulting to `~/.codex/pstack-codex/`. Native and mixed preferences use one current schema 1. The new identity supplies no old-state reader, old-name alias, or automatic migration. An old install must unregister through its own setup and be removed before a fresh install.

On both hosts, setup starts with worker executor selection. It checks installation and authentication only for selected CLIs, guides authorized installation and required human login, then collects supported models, roles, and budget for review and saving. It reuses existing authentication without copying credentials. An unselected external CLI is not a prerequisite. Setup finishes with saved configuration and discovery-refresh guidance. A first real task runs when execution verification is requested. The parent chat stays on its native host and model. Required model-family gates remain local to their workflow step.

Registration manages only owned definitions and exact config blocks. It preserves unrelated settings, comments, modes, and preferences. User edits, unowned role conflicts, symlinks, damaged ownership and concurrent changes remain explicit errors. Updates require rerunning setup and new-session role discovery. Before removal, unregister while the bundle exists. Native plugin removal supplies no cleanup hook. Preferences remain unless deliberately reset.

## Claude Code adaptations

### Target and role selection

The [accepted host design](claude-host-design.md) and [separate-distribution decision](adr/0001-separate-host-distributions.md) define the product. Claude uses the same nine role keys with scalar and list shapes. Setup saves its own host preferences under `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/`. It leaves Codex preferences unchanged. Every real entry preserves executor, exact model, and reasoning effort. Parent aliases bind to the actual native Claude parent.

Setup shows unresolved proposal slots and saved choices. It selects worker executors before conditional CLI preparation, then supported exact models, roles, and budget. It changes no orchestrator model. Native generated agent variants preserve each original worker body and exact selected Claude model. Native Claude capability records accept `low`, `medium`, `high`, `xhigh`, and `max`, and a saved Claude preference entry must be at `xhigh` or below; Codex selections retain their separate supported effort domain. Unsupported native efforts fail before saving or resolving and leave existing preferences unchanged. User edits and ownership conflicts remain explicit rather than being overwritten. Updates and restores require rerunning setup. Removal first unregisters owned agents while the bundle exists and retains preferences.

Earlier Claude bundles accepted moving aliases with context modifiers such as `sonnet[1m]`, despite the exact-model contract. Current setup and delegated workflows reject those saved preferences before resolving any role, and leave the file unchanged. Before rerunning setup, replace them in `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/models.json` with account-supported exact model IDs and reasoning efforts. Plain `auto` and `inherit-parent` keep their native-parent behavior.

An explicit `--claude-home` selects the preferences and definition target. CLI capability and authentication probes inherit the running host's environment, including its existing `CLAUDE_CONFIG_DIR`. Detection reports those two scopes separately. It does not relocate or copy credentials into the preferences target.

Execution before setup remains available. Unsaved roles use the actual native parent through static inherited agents at their original cardinality. Setup suggestions remain separate from those execution fallbacks. Readonly source sites use native definitions that exclude Write, Edit, and NotebookEdit. How's single seat uses the `read-only` kind. Recall's per-source investigators use `general-purpose` and keep full tool access, including MCP. Reflect reads the transcript itself and starts no subagent. How's seat and recall's investigators have no role and run on the actual native parent. A Bash-capable agent is not an OS-level readonly boundary.

Registration retains owned model variants until explicit unregister, so staging another model cannot delete definitions referenced by saved preferences. Unselected variants retain their previous bodies until selected again or removed through unregister.

### Workflow and execution binding

[Claude Code execution](../plugin-claude/skills/poteto-mode/references/execution.md) is the shared delegation reference. Native Claude selections use Agent with setup's exact-model definition. Codex selections use a foreground task command in native background Bash. The task remains attached until its real terminal outcome. The runner starts Codex threads with `on-request` approval and the `auto_review` reviewer. It starts them in `workspace-write` and refuses `read-only`, so a no-edits task relies on its brief and the parent's `git status` check, as native Claude and agy workers do. The bundled runtime defaults to `never`, which leaves a worker no way to request escalation, so browser checks, local servers, Git writes, and network access fail inside the macOS sandbox. The bundled [official runtime decision](adr/0002-bundle-codex-worker-runtime.md) defines the source dependency. No universal worker scheduler or relay agent is added.

The saved `codexWorkers` setting selects the worker command. `hidden`, the default, is the official standalone `codex-app-server --session-source app-server`. `visible` is the Codex CLI's `codex app-server`, for hosts that cannot obtain the standalone package; its worker threads appear in Codex history. See [ADR 0004](adr/0004-codex-worker-visibility-setting.md). The host running setup chooses the value, explains it, and prepares the selected dependency from [official sources](https://github.com/openai/codex/releases), including installation when needed and PATH availability to future workers. Absolute-path flags are per-invocation diagnostics overrides, not saved installation settings. The npm CLI is the human login tool and, with `visible`, also the worker server. Pstack owns the invocation and readiness checks; native distribution, release pinning, upgrades, and cross-version compatibility management remain outside its role. See [ADR 0002](adr/0002-bundle-codex-worker-runtime.md). No custom installer, updater, process wrapper, alternate profile, or automatic fallback between the two servers is added.

The runner owns one executable and argument array shared by inspect, availability, and actual launch. The vendored client and availability function accept optional `appServerArgs`; omission preserves the upstream `codex app-server` behavior. Detection retains schema version 1 and its legacy `cli` container while recording runtime kind, executable, arguments, and version. Bounded version and source-help checks reject missing or unsupported servers before connection or thread creation. With `hidden`, help must advertise `--session-source`; that check does not establish its semantics or Desktop visibility. With `visible`, `codex app-server --help` must succeed. The runner reads `codexWorkers` from the Claude home for every run, and `--codex-workers` overrides it only for detection and catalog probes. Requests, results, and spawn diagnostics retain safe launch identity without credentials.

The standalone source replaces the failed hidden-tag policy. New roots send no `threadSource` and remain persistent. Exact resumes keep their original source, including older visible threads. Workers share account, configuration, rollout files, and state through inherited `CODEX_HOME`. The runner preserves direct process ownership, sandbox selection, reviewed approvals, cancellation, native descendants, terminal status precedence, and exact thread continuation. No old thread records are migrated.

Sandbox restrictions alone do not establish that an authorized worker task is unavailable. Parent launch guidance covers browser, local-server, and network requirements in both directions. Codex workers can request reviewed escalation. Claude processes inherit their launcher's OS permissions and retain their own tool permissions. Coordinators inspect the actual command and approval outcome before changing the assignment. The vendored Codex client rejects server-initiated approval requests. Automatic review can decide internally, but a request that falls back to that client remains an unsupported capability. Changing executors does not override a denial.

The [delegation inventory](../plugin-claude/skills/poteto-mode/references/delegation-sites.json) accounts for role consumers and host-specific sites. Panels keep duplicate seats and cardinality. The Arena judge pool retains its ordering, parent-vendor comparison, unknown-parent behavior, and disclosed skip. It has no hidden default retry. Required different-model and different-family verifiers still require eligible selections. Retry, dropout, fresh-worker, worktree, and parent-review rules remain the calling workflow's rules.

Upstream cloud workers map to exclusive local worktrees with separately assigned machine resources. A new worktree gets its ignored dependency and build directories from the repository's own setup or install inside that worktree, never from a link to another checkout, per the same [worktree setup reference](../plugin-claude/skills/poteto-mode/references/worktree-setup.md). A history fork copies no files or processes. Interrogate transfers scoped tracked and untracked input into each worktree and the parent reruns findings. A native poteto-agent receives the actual skill path and uses the full body before work, from complete supplied context or an actual read. Chain-following assessment inspects the actual input, required missing-body reads, and worker actions or code shape. Supplied content alone does not prove compliance.

[Claude history](../plugin-claude/skills/recall/references/claude-history.md) scopes transcripts to a repository and its registered worktrees. [Native wakeups](../plugin-claude/skills/poteto-mode/references/claude-wakeups.md) map session schedules, persistent schedulers, and configured webhook channels to their actual capabilities. ## Antigravity executor adaptation

Both hosts accept `{executor: "antigravity", model, reasoningEffort}` in their existing schema 1 role shapes. This additive adaptation lets users select the official agy CLI without an unofficial extension. It preserves sparse saves, original cardinality, ordered duplicates, native fallback, and model-family gates. Parent aliases stay native. Provider and authentication fields are invalid for this route. Native registration creates no Antigravity agent definitions.

`agy-capabilities.mjs` owns exact-entry validation and source-labeled per-model capabilities. Normalization retains provenance and optional runtime version. Global effort syntax never becomes a model capability matrix. A fixed-effort label establishes only its reported variant's configured availability. Budget mapping preserves the exact ID and returns `needsChoice` when no supported effort meets the target. Offline read and resolve need no agy executable or catalog.

`run-agy.mjs` requires the official CLI 1.5.8 or newer and owns one headless stream process group. It sends the complete task and explicit context through one stream-input user event, closes stdin, and passes `--dangerously-skip-permissions`, so agy approves every native tool request. It inherits official authentication and environment. It reads no credentials and changes no personal defaults. The native CLI owns its tools, customizations, conversation storage, and history. Parent MCP, complete conversation, permissions, and native role registration do not transfer.

Authentication follows the Codex executor. Setup lets the user choose subscription login, the Gemini API key method, or ADC, prepares the chosen method with the official guidance, and never switches methods silently. For the API key method, setup sets `modelProvider: "gemini"` in agy's settings file. The user supplies `GEMINI_API_KEY` through the inherited environment, outside the conversation. The runner passes no authentication option. Detection and every receipt carry one `auth` object derived from inherited state in a fixed order. `method` is `gemini-api-key` when agy's settings set `modelProvider` to `gemini`, otherwise `adc` when `AGY_ADC_AUTH=true`, otherwise `inherited-default`. `modelProvider` is the only value read from `~/.gemini/antigravity-cli/settings.json`, and it is null when that file is absent or unreadable. `geminiApiKeyPresent` records whether the variable is nonempty, never its value. `verified` stays false because nothing probes authentication. The receipt's `authMode` equals `auth.method`.

Success requires matching init and terminal conversation identities, one successful or recovered terminal result, a nonempty answer, and orderly zero-exit process closure. agy writes a recovered result after it retried a failed model call and finished the turn. That result has status `ERROR`, finished reason `error`, and the last retried error, and the CLI exits 0 after it. The receipt is then completed and records that error as `recoveredError`. Closure gives the CLI's process group 3 seconds after the CLI exits to empty on its own, because MCP servers from agy's own configuration can still be shutting down, and kills the group and fails the run if any member remains. Any error, cancellation, or timeout overrides a late apparent answer. A failed run keeps the native terminal result as `terminalResult`, with its native `status`, `error`, `finished_reason`, and `usage`, and the receipt's `usage` follows from it under the same conversation-cumulative label. Receipts keep requested settings separate from the CLI-observed model. Effective effort remains unknown when unreported. Usage is conversation-cumulative and cannot be added to a predecessor's usage as a per-turn total.

Every run receipt records `stop`. A `timed-out`, `interrupted`, or `terminated` run is `interrupted`, with the cause `deadline`, `SIGINT`, or `SIGTERM`. Any other unsuccessful run is `error`. The request and receipt record `timeoutMs`. A tool step in an error state, such as a read of a missing file, goes to `toolErrors`, and the run continues. Any other failed step still ends the run.

Headless agy cannot ask for a permission. A tool request that no allow rule covered ended the run with no answer. On 2026-11-17 four Carbon code runs ended after 83 to 162 seconds without a change. ## Stopped worker continuation

Upstream poteto-mode gives a retry to a fresh subagent with consolidated scope. It reuses an existing subagent only when new work needs state that lives in that agent and is costly to move, and it names a local checkout, uncommitted changes, and a running process. Upstream's Cursor workers keep that state on their own machines, and its `Task` tool sets no deadline.

Local executors keep the checkout and changes in the parent's worktree, and a running process ends with its worker. The state that lives only in a local worker is its conversation. A worker that stopped before its result still holds the reads, tool results, and reasoning it finished there. The [continuation reference](../plugin-claude/skills/poteto-mode/references/continuation.md), common to both targets, treats that conversation as the costly state and continues it. A fresh worker takes the work when the result is wrong, the conversation cannot continue, or the calling workflow's retry by cause asks for another model or scope. After two continuations stop for the same cause, the calling workflow's retry limit applies, such as Orchestrate's drop and replan. Each continuation repeats the consolidated brief and names the cause of the stop. Upstream warns that interrupt-chained resumes drop directives. The repetition puts every earlier directive in the continuation message itself. No check yet measures directive retention across several interruptions. Upstream's `SKILL.md` text is unchanged, and both execution references link the binding.

Before this change, the agy runner continued only a successful receipt. The Codex and Claude runners accepted any exact ID, but their guidance still sent a stopped worker's retry to a fresh worker. On 2026-11-17 a parent-chosen 540-second deadline stopped a Carbon investigation after 105 steps, and the fresh retries read the same files again. Each runner now records `stop` with `kind`, `cause`, and `continuable`. The kinds are `completed`, `interrupted`, `permission`, and `error`. Codex marks a run with denied reviews as `permission`, which leads to the existing approval retry. Claude marks a run with `permission_denials` as `permission`. agy approves every tool and never reports `permission`.

## Worker runner runtime

The Codex, Claude, and Antigravity worker runners follow [Orca](https://github.com/stablyai/orca) at commit 84f67831, per [ADR 0005](adr/0005-follow-orca-for-worker-runners.md). The shared `worker-runtime.mjs`, `worker-supervisor.mjs`, and `workers.mjs` scripts are identical in both targets.

Each runner starts its CLI under Orca's POSIX provider supervisor. The supervisor is spawned detached, runs the CLI in its own process group, and stops that group when the runner exits, is signalled, or dies. It detects a dead owner when its parent pid changes. Its stop ladder is: stdin end, 1000 ms, SIGTERM to the group, 3000 ms, SIGKILL, and a group reap bounded at 1500 ms. Codex runs as a session, so stdin end alone starts the ladder. Claude and agy end stdin after the prompt, so for them only an explicit stop starts it. The CLI writes directly to the runner's stdout and stderr instead of through Orca's relay, because the relay hid the CLI's end of output from the runner. The child environment drops Orca's list of parent Claude and Codex session variables. For agy it also drops `GEMINI_API_KEY` and `GOOGLE_API_KEY` and sets `AGY_CLI_DISABLE_AUTO_UPDATE=true`.

Each run writes `events.jsonl` in its run directory and one registry file under `$PSTACK_STATE_HOME`, else `$XDG_STATE_HOME/pstack`, else `~/.local/state/pstack`. A registry file is written once, so concurrent runners never share a writer. `workers.mjs status` derives each run's state from its run directory: `running`, `lost`, or the receipt's stop kind. `workers.mjs follow` streams one run's events and exits when the receipt appears or the runner dies without one. Receipts add `stop.code`, a typed cause. `stop.cause` and receipt errors are redacted with Orca's credential rules and keep at most the last 2000 characters. Raw diagnostics stay in the run directory.
