# Design and compatibility

## Purpose

The pstack project distributes skills and agents as separate Codex and Claude Code plugins while retaining a reproducible relationship to the same upstream sources. The Codex product is `pstack-codex`; the Claude Code product is `pstack-cc`. Users install through their host's native marketplace and run setup to register agents and select worker executors and models. Development and artifact commands are documented in [Maintenance](stack.md); installation and usage are in the [README](../README.md).

## Sources and reproducibility

- [upstream.lock.json](../upstream.lock.json) pins the complete pstack snapshot and the Codex source revision used for inspection.
- [dependencies.lock.json](../dependencies.lock.json) pins the selected cursor-team-kit skills (`control-ui`, `control-cli`, and `deslop`) and their license.
- [distribution-policy.json](../distribution-policy.json) excludes Benny Slack reporting automation from the distribution. The reference snapshot remains intact; general Slack research is retained. New Benny entry points or references require review rather than silent reintroduction.
- [codex-runtime.lock.json](../codex-runtime.lock.json) pins the official Codex worker snapshot, selected file mappings, and digest. Its locked source lives under `upstream/codex-runtime/`.
- [patches/claude/series](../patches/claude/series) orders the Claude adaptations over the policy-filtered pristine source, selected cursor-team-kit files, and pinned official runtime. It does not replay the Codex adaptation series.
- [patches/series](../patches/series) orders the Codex adaptations. The patch baseline combines the policy-filtered pstack snapshot with the selected cursor-team-kit source files, so new upstream content is applied before the adaptations.

Approved common adaptations are stored once in `patches/shared/`. Both ordered target series use `shared/NNNN-name.patch` references. How, its explainer template, and No comments use common bodies; native invocation and executor controls remain in each target's `skills/poteto-mode/references/execution.md`. A target-local full deletion followed by a shared addition transfers these files without changing historical patches. The two complete output trees remain self-contained Git installation inputs. See [the shared-authoring decision](adr/0003-shared-workflow-adaptations.md).

Source snapshots are reference material, not instructions for agents working on this repository. Codex adaptations live in `plugin/`; Claude Code adaptations live in `plugin-claude/`. Both retain upstream attribution and licenses. Source lock hashes cover sorted relative paths and file bytes; patch replay and artifact verification additionally compare file types and permissions. Symlinks are rejected.

The repository's `.agents/plugins/marketplace.json` exposes the committed `plugin/` tree through Codex's Git marketplace support. Consumers can install from the GitHub URL without building the maintainer CLI. The Git and generated local marketplaces share the `pstack-codex` identity.

The root `.claude-plugin/marketplace.json` exposes committed `plugin-claude/` as `pstack-cc`. A generated artifact for either target contains its selected tree under `plugin/`, native marketplace metadata, and `artifact.json` with source, patch, integrity, and recorded compatibility metadata. Codex keeps artifact schema 1. Claude Code uses separate schema 2 with target `claude-code` and its runtime lock. A fixed local marketplace can select a verified child artifact without rewriting older artifacts. Local artifact selection, installation into Codex's cache, setup, and runtime execution are separate operations.

## Codex adaptations

### Invocation and agents

The distribution preserves the upstream skill structure and explicit-invocation policy. `agents/openai.yaml` maps upstream `disable-model-invocation` declarations to Codex invocation metadata while retaining the original frontmatter. The technical names of `poteto-mode` and `make-bot-ui` use their directory slugs for callable tokens; their upstream display names remain in interface metadata.

The two upstream agent instruction bodies are also supplied as native TOML definitions. The poteto-agent body keeps upstream's fallback for a missing skill path, but it searches the installed `pstack-codex` plugin instead of Cursor's plugin directory. Setup registers them and a description-only `pstack-general-purpose` role. The latter carries requested model and reasoning choices without replacing the user's existing default role or adding another instruction body.

### Execution and model selection

The original 17 role keys and each host's persistence shapes remain. Codex stores arrays for every role. Claude keeps scalar entries or aliases and ordered lists. Both saved configurations start with empty `roles`. A separate setup proposal exposes all roles and unresolved scalar-one or panel-two slots. A sparse accepted save is valid. Missing roles resolve transparently to the actual native parent, with source `unconfigured` and original cardinality. This replaces the prior fixed-model and unsaved native Opus fallbacks. Before setup, an unconfigured general-purpose seat without the registered pstack role uses the host-supported native general-purpose or default path with the selected model, effort, and complete task brief. Explicit task-native counterparts or arms keep their exact model and effort. Only parent-alias selections bind to the actual parent. If the host cannot preserve the selected settings, the seat reports a specific capability gap. Saved selections retain registered routing. The `poteto-agent` and `comment-sicko` custom roles require setup registration, so workflows that need them cannot run before setup.

Saved exact entries take precedence. Model IDs, efforts, and executors are separate fields. Task-specific effort adjustments apply to exact selections. Parent aliases preserve the actual parent model and effort and bind to the actual native host parent and do not establish a different-family relationship. Unknown families do not establish diversity. Sonnet and Opus belong to the same Claude family. Required verifiers use eligible exact entries already resolved by the calling workflow, in existing order, or an explicit task counterpart. They do not scan unrelated roles, add a verifier role, or rank alternatives. An unmet requirement keeps that step's existing gap outcome.

Arena preserves seat counts, dropout padding, ordered eligible judges and the unknown-parent rule. It now uses only the selected pool. Hidden family-default recovery and a default-pool retry were removed because they could dispatch an unchosen vendor or model. If no eligible selected judge runs, Arena discloses and skips the judge. This approved adaptation does not waive another workflow's required verifier.

Claude capability records retain executor, exact model, supported efforts, and per-model `host`, `configuration`, or `manual-confirmation` evidence. Runtime detection proves CLI version and syntax, with safe authentication status separate. It supplies no model capability or bundled default. Normalized catalogs retain provenance across repeated normalization. Offline read and resolve retain saved IDs without a live catalog.

`run-claude.mjs run` requires `--model EXACT_ID`, forwarded separately from effort and recorded in request metadata. Instruction and skill files are optional transport inputs; callers still provide the context their task requires. Omitted effort uses the existing Claude CLI default and records a null request effort, without a bundled fallback. A missing `--model` fails before worker launch. `observedModel` comes from the stream and may differ or be absent. Requested effort is not observed effective effort. Explicit resumed requests keep the original exact model. Existing sessions, permissions, process signals, and result handling remain.

Upstream cloud-first workers are adapted to local worktree execution. The parent passes the task, selected instructions, and required context paths to the chosen executor. Both outbound wrappers automatically add the receiving executor's identity and one shared worker-context body to the task input.

The wrappers read supplied role, instruction, and skill paths and deliver their complete instruction bodies in deterministic code. The parent supplies paths instead of copying those bodies into its brief. Workers apply complete bodies already in context without reopening their files, including nested requests to read the same file. Paths, summaries, excerpts, and truncated bodies do not satisfy that exception. Required linked references and applied principle leaves still need their complete bodies or actual reads. Delivery establishes available instructions, not behavioral compliance.

Launching-host role preferences remain authoritative; native tool names and parent launch recipes are interpreted in the receiving harness. The original asynchronous delegation requirement remains. Native Claude `Agent` or `Task` calls use `run_in_background: true` when exposed; native Codex uses its asynchronous handles without an invented field. This adds no CLI flag, plugin registration, or permission change. This does not provide a read-only enforcement boundary or imply that an external Claude process inherits the parent's complete conversation. Managed worktrees use the host's attachment and archive lifecycle; recurring automation records its concrete local repository before scheduling.

Conversation inheritance and filesystem preparation are separate operations. A native history fork does not copy uncommitted changes or running processes into a new worktree. Interrogate prepares each review worktree with the scoped working-tree changes and keeps only failures the parent reruns against the real code. Follow the actual host's model, effort, role and history controls; use a fresh context with a complete brief when that host disallows overrides on a full-history fork. The [official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) describes configuration precedence, while the exposed tool schema controls the active invocation.

### Workflow changes in pstack 0.15.36

Orchestrate uses native coordination and a local project tracker/store instead of the deleted `orch` CLI, fixed TSV/JSON ledger and drain protocol. Each PR has one owner and a non-author verifier from another model family at its current head. Its Codex mapping preserves the upstream prohibition on orchestration scripts and polling loops. The existing Claude executor launcher remains an execution binding. PR/CI subscriptions are used only when the host exposes them; native child completion tools do not imply a PR event subscription.

Autopilot-stack follows Autopilot-full without merging and stacks only real dependencies. The upstream review bar blocks proven user-facing bugs, failed gates and shipped documentation made wrong by the change. Pre-existing base defects become follow-ups unless copied or newly reached. Wording-only changes do not require a new verifier, and opening a PR no longer automatically runs Interrogate. Interrogate's output excludes unrun concerns, so no verified findings is narrower than absence of risk. Sharpen produces a rewritten prompt rather than executing the underlying task.

The new explicit-only `statechart` and `ketchup-video` skills retain their upstream scope. Statechart checks a TLA+ model and derives Mermaid and rule-violation paths from the checked graph. It still requires reproducing a modeled code defect against the real implementation. Its first real check may install Java/TLC through mise, and SVG rendering uses Pele. Ketchup-video specifies an evidence-based subtitled video workflow without bundling a renderer. Updating the plugin does not execute either workflow or install those tools.

### Setup and ownership

Setup stores role preferences under `$CODEX_HOME/pstack-codex/`, defaulting to `~/.codex/pstack-codex/`. Native and mixed preferences use one current schema 1. The new identity supplies no old-state reader, old-name alias, or automatic migration. An old install must unregister through its own setup and be removed before a fresh install.

On both hosts, setup starts with worker executor selection. It checks installation and authentication only for selected CLIs, guides authorized installation and required human login, then collects supported models, roles, and budget for review and saving. It reuses existing authentication without copying credentials. An unselected external CLI is not a prerequisite. Setup finishes with saved configuration and discovery-refresh guidance. A first real task runs when execution verification is requested. The parent chat stays on its native host and model. Required model-family gates remain local to their workflow step.

Registration manages only owned definitions and exact config blocks. It preserves unrelated settings, comments, modes, and preferences. User edits, unowned role conflicts, symlinks, damaged ownership and concurrent changes remain explicit errors. Updates require rerunning setup and new-session role discovery. Before removal, unregister while the bundle exists. Native plugin removal supplies no cleanup hook. Preferences remain unless deliberately reset.

## Claude Code adaptations

### Target and role selection

The [accepted host design](claude-host-design.md) and [separate-distribution decision](adr/0001-separate-host-distributions.md) define the product. Claude uses the original 17 role keys and scalar/list shapes. Setup saves its own host preferences under `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/`. It leaves Codex preferences unchanged. Every real entry preserves executor, exact model, and reasoning effort. Parent aliases bind to the actual native Claude parent.

Setup shows unresolved proposal slots and saved choices. It selects worker executors before conditional CLI preparation, then supported exact models, roles, and budget. It changes no orchestrator model. Native generated agent variants preserve each original worker body and exact selected Claude model. Native Claude preferences and capability records accept `low`, `medium`, `high`, `xhigh`, and `max`; Codex selections retain their separate supported effort domain. Unsupported native efforts fail before saving or resolving and leave existing preferences unchanged. User edits and ownership conflicts remain explicit rather than being overwritten. Updates and restores require rerunning setup. Removal first unregisters owned agents while the bundle exists and retains preferences.

Earlier Claude bundles accepted moving aliases with context modifiers such as `sonnet[1m]`, despite the exact-model contract. Current setup and delegated workflows reject those saved preferences before resolving any role, and leave the file unchanged. Before rerunning setup, replace them in `${CLAUDE_CONFIG_DIR:-~/.claude}/pstack-cc/models.json` with account-supported exact model IDs and reasoning efforts. Plain `auto` and `inherit-parent` keep their native-parent behavior.

An explicit `--claude-home` selects the preferences and definition target. CLI capability and authentication probes inherit the running host's environment, including its existing `CLAUDE_CONFIG_DIR`. Detection reports those two scopes separately. It does not relocate or copy credentials into the preferences target.

Execution before setup remains available. Unsaved roles use the actual native parent through static inherited agents at their original cardinality. Setup suggestions remain separate from those execution fallbacks. Readonly source sites use native definitions that exclude Write, Edit, and NotebookEdit. Why and Reflect retain full tool access. A Bash-capable agent is not an OS-level readonly boundary.

Registration retains owned model variants until explicit unregister, so staging another model cannot delete definitions referenced by saved preferences. Unselected variants retain their previous bodies until selected again or removed through unregister.

### Workflow and execution binding

The pinned official runtime originally framed app-server stdout with Node's `readline`. On the observed Node.js 24.22.2 runtime, that reader also splits literal U+2028 and U+2029 characters inside valid JSON strings. The adapted direct client uses its existing LF-only buffer instead. The shared configuration probe uses the same delimiter rule with UTF-8 decoding. Both readers preserve Unicode content and the final record without a trailing LF, while retaining their malformed-record errors and shutdown behavior. This repair is recorded in new adaptation patches without changing the locked upstream snapshot.

[Claude Code execution](../plugin-claude/skills/poteto-mode/references/execution.md) is the shared delegation reference. Native Claude selections use Agent with setup's exact-model definition. Codex selections use a foreground task command in native background Bash. The task remains attached until its real terminal outcome. The bundled [official runtime decision](adr/0002-bundle-codex-worker-runtime.md) defines the source dependency. No universal worker scheduler or relay agent is added.

Normal Codex workers use native `on-request` approval and the `auto_review` reviewer without an additional launch flag. This host binding preserves the workflow's delegate responsibilities and required verification. The launcher confirms the effective policy, reviewer, and sandbox class before each task turn, including exact resume. Missing support or substituted settings fail before the task runs. Reviewed execution cannot use `danger-full-access`. An explicit `--approval-mode never` retains deliberately noninteractive tasks; it does not turn blocked required checks into successful verification.

Approved escalated commands execute outside the sandbox under the existing Codex reviewer policy. The launcher checks sandbox class, not an independent network or writable-root allowlist. It does not install a new policy or unconditionally accept requests. The confirmation gate precedes a turn but can leave an already-created or resumed thread, whose ID remains in the receipt. Requested and effective settings, unsupported server requests, and raw review evidence remain in the receipt and diagnostics. A completed turn does not prove every task check passed.

The macOS command boundary adds a runtime guard for external Codex workers and registered native pstack worker roles. A scoped shell command that still runs under Seatbelt exits with `PSTACK_REVIEW_REQUIRED` before its original body starts. A native reviewed retry can execute outside that sandbox. This covers nested interpreter launches as well as direct browsers. It does not classify Chrome command strings, approve actions, grant new authority, alter model routing or transfer verification to the coordinator. All scoped macOS shell commands encounter this gate, so reviewed retries can add approval-model usage.

The shared hook script derives native role scope from setup's ownership record. External workers receive per-process hook configuration and an external-worker marker. Before a task turn, the runner confirms the exact enabled, trusted hook and rejects unsupported or ambiguous rewrite configurations. It trusts only the discovered owned key/hash in the process configuration, preserving other trust and authentication state. Native setup trusts only the installed pstack hook through supported config writes and reads it back. An update must refresh hook trust along with owned agent definitions.

The native `.codex-plugin/plugin.json` manifest declares the skills, onboarding, interface metadata, and lifecycle hooks. Root `plugin.json` retains matching package metadata without an Agent Plugins schema declaration. Codex prioritizes a schema-declared root manifest and omits hooks for that format. The native manifest uses Codex's hook-capable legacy format and takes precedence over unchanged upstream Cursor metadata. Automated checks keep its identity, onboarding, and interface metadata consistent with the root package metadata.

This is a runtime guardrail on supported shell tool paths. The host can fail open on hook error or timeout. Native root-chat commands, unrelated roles, pre-existing interactive processes and specialized non-shell tool paths are outside its scope. It is not security isolation against a malicious user or a guarantee when hooks are disabled. Source-read-only intent still applies to an approved host command, without an OS-enforced source-write boundary.

The [delegation inventory](../plugin-claude/skills/poteto-mode/references/delegation-sites.json) accounts for role consumers and host-specific sites. Panels keep duplicate seats and cardinality. The Arena judge pool retains its ordering, parent-family comparison, unknown-parent behavior, and disclosed skip. It has no hidden default retry. Required different-model and different-family verifiers still require eligible selections. Retry, dropout, fresh-worker, worktree, and parent-review rules remain the calling workflow's rules.

Upstream cloud workers map to exclusive local worktrees with separately assigned machine resources. A history fork copies no files or processes. Interrogate transfers scoped tracked and untracked input into each worktree and the parent reruns findings. A native poteto-agent receives the actual skill path and uses the full body before work, from complete supplied context or an actual read. Chain-following assessment inspects the actual input, required missing-body reads, and worker actions or code shape. Supplied content alone does not prove compliance.

[Claude history](../plugin-claude/skills/recall/references/claude-history.md) scopes transcripts to a repository and its registered worktrees. [Native wakeups](../plugin-claude/skills/poteto-mode/references/claude-wakeups.md) map session schedules, persistent schedulers, and configured webhook channels to their actual capabilities. Native child completion is not a PR subscription. Orchestrate preserves its prohibition on orchestration scripts and polling loops. A missing remote VM, scheduler, or inbound channel is reported at that specific step rather than silently disabling a workflow with an available local mapping.

Claude Code's [subagent reference](https://code.claude.com/docs/en/sub-agents), [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference), [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks), and [channels reference](https://code.claude.com/docs/en/channels-reference) support the host mapping. Source documentation establishes supported controls, not execution on this bundle or account. The runtime's tool schema and observed results determine the actual behavior.
