### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers through their selected executor per `references/codex-execution.md`, using native collaboration controls on the Codex path. Keep the program's state in the local task tracker (`notes.md`) and the local task store below. Watch each PR with PR and CI event subscriptions when the host exposes them. Native child completion events and waits cover delegates. If the host has no PR subscription, report that capability as unavailable and inspect PR state at decision points. Run no orchestration scripts or polling loops, and never relay messages or status between agents. The existing role-selection helper and Claude executor runner in Codex execution remain the execution bridge, not a bookkeeping runtime or watcher.

#### Store layout

Resolve, create, and record one absolute local task-store path before spawning. Use the caller's explicit path or `<project>/.local/pstack/orchestrate/<project-slug>/`. Keep `notes.md`, briefs, reports, and required evidence there, outside the installed plugin cache, and pass the same absolute path to every owner and replacement. Each mutable file has one writer. Choose the tracker shape for this program.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including the complete upstream reports it depends on. Pass their absolute paths and required skill paths through Codex execution, with the applicable constraints in the consolidated brief. Workers do not inherit their siblings' conversations. Run each worker in an exclusive local Git worktree and branch through its selected executor. Bind every command to its assigned checkout and every input and output to an absolute path. Worktrees share the host, credentials, and machine resources. Assign separate ports, data directories, simulator resources, and sessions, or serialize a resource that cannot be separated. Use `control-ui` or `control-cli` bundled from the pinned `cursor-team-kit` source for runtime checks. Read history only through the **recall** skill's project-scoped helper. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Carry built state when new work needs it.** Codex execution distinguishes conversation history from checkout and process state. Give a fresh worker the consolidated brief and transfer or hand over its predecessor's checkout state when feasible. Reuse the state holder only under poteto-mode's exception for a costly-to-move checkout, uncommitted changes, or a process it still runs. `fork_turns` copies conversation, not an independent environment. Message a worker only for a follow-up on the same work, using the selected executor's asynchronous controls. Inspect native agent status or the external process and receipt to check on it. Do not restart an idle worker for a status check.
- **Each PR gets a verifier that isn't its author,** on a different model family. Select the Sol or Opus counterpart through Codex execution. If no required counterpart can run, record the capability gap and keep the PR unverified. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model through Codex execution after a tool error. This retry requires a different model, not a different family. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
